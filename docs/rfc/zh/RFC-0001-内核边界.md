# RFC-0001: Nous AI 内核边界

- **状态:** 草案
- **日期:** 2026-08-04
- **作者:** Nous 内核架构组

## 1. 问题

当前 Nous Runtime 没有强制执行的内核边界：

1. **三个不兼容的 Task 模型** — 各自被不同子系统使用，互不协调
2. **30+ 个独立 Registry 类** — 各自维护独立的持久化、索引和生命周期
3. **两个并行事件系统** — RuntimeEventBus 和 EventStream，不同 schema
4. **产品层绕过内核** — 桌面、CLI 和 HTTP API 直接调用 Provider
5. **无可信计算基** — 所有代码在同一 Python 进程中运行

## 2. 约束

1. 必须保留现有功能
2. 必须保留现有数据
3. 不能一次全部替换
4. 必须支持当前平台

## 3. 内核边界

**Nous AI Kernel** 是最小可信计算基，负责：
1. 所有权威状态
2. 资源准入和隔离
3. Workload IR 的验证和执行
4. 模型、引擎和设备的生命周期管理
5. 提供一个统一入口（NKI）

### 可信计算基 (TCB)

在 TCB 内：nousd、核心类型、状态机、资源管理器、安全门、NKI、日志、最小加密

不在 TCB 内：模型引擎、设备驱动、第三方插件、Python 运行时、产品应用

### 入口统一

所有外部通信收敛到 NKI。内核只有一个入口。

## 4. 安全与所有权

每种持久状态只有一个权威所有者。系统服务通过 NKI 提交的 workload 拥有其数据，但内核拥有执行状态。

## 5. 兼容性

分 6 个阶段迁移：
1. 定义边界，创建 Rust workspace，编写 schema
2. 实现 nousd（NKI、日志、状态机）
3. 模型/引擎/设备注册迁移到 NKI
4. Workload 提交迁移到 NKI
5. 完全内核接管
6. 移除废弃路径

## 6. 验收标准

- [ ] 内核边界文档已发布
- [ ] Rust workspace 在 Linux x86_64 和 Windows ARM64 上编译通过
- [ ] NKI v1 schema 已定义
- [ ] nousd 启动、接受 NKI 请求、记录状态
- [ ] 现有 Python 测试套件通过
- [ ] 100% 的内核状态转换通过日志
- [ ] 0 处产品代码绕过 NKI
